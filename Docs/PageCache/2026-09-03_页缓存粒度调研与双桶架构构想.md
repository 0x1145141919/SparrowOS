## 0. 一句话摘要

在 QD1 阻塞语义下，NVMe 单命令固定成本 ~60µs（实测），数据边际成本仅 0.198µs/KiB
→ **"少发命令"是唯一要紧的事**：顺序流量靠聚合（≤1MiB/mdts），随机流量靠并发（QD），
粒度管的是"抓取/驱逐/写回"的形态。页缓存最优形态 = 三层解耦（4K 扇区脏跟踪 + 自适应预读 + 对象单元），
双桶（4K 区间 / 32K 区间）是合理的工程化落地路径，但 v1 就必须埋 live 率指标，转换用"驱逐+缩边"而非搬数据。

## 0.5 架构锚点现状（2026-09-03 勘误，来自设计方）

旧 `page_v2设计演进记录.md`（page_cache_node_t 挂 struct page）与 LRU/SWAP 草案已**废弃/转生**，
代码中无残留（grep page_cache_node_t 零命中）。现状与规划：

1. **`page_frame_state_mgr`**（page_frame_state_mgr.h）：原 all_pages_arr 重构后的唯一权威账本——
   `pages_arr`（`sizeof(page)==1`，1B/页 纯类型标记）+ `intervals[]`（phyaddr→mem_map 下标二分表）+
   `early_alloc`（FreePagesAllocator::Init 末尾才 close）。**唯一使命 = 页框类型标记/状态**，
   收养即冻结不覆写。free_segs 概念废弃：FPA 进化成"从脏 order-0 向上折叠"，直接拿 intervals_snapshot()。
2. **页缓存元数据 ≠ 这个账本**：规划为**另一组独立元数据数组**，与 mem_map 平行，
   物理地址线性索引（代表地址语义），在 `mem_init.cpp` 的**前 FPA 时期**一次性分配就位
   （early_alloc 尚开，或走 pages_arr_file / fpa_bitmaps 同款资产穿越+adopt 模式）。
3. 对本调研的意义：§7.2 的"索引层按 4K 扇区叶子"与该数组天然吻合——页缓存元数据按 4K 页框
   一条（O(RAM/4K) 固定开销），32K 对象 = 8 个连续条目聚合，双桶/多粒度索引无需另起炉灶；
   LRU/驱逐等动态结构放条目内或旁挂。

## 1. 动机与问题定义

- 4K 粒度"伤"在哪：单命令固定往返 ~60µs 摊到 4K 上，顺序读吞吐被命令数卡死（QD1 时 4K 命令 ≈ 16K IOPS ≈ 64MB/s 天花板）
- 大粒度担心什么：写放大（部分更新被迫重写整单元）、驱逐浪费（热点 4K 的邻居占住缓存）、
  分配碎片（伙伴高阶）、CPU 污染（归零/校验随 g 线性涨）
- 核心认知：**"页缓存粒度"同时管 4 件事（抓取/索引驱逐/脏跟踪写回/分配），它们对 g 的单调方向相反，
  先解耦再优化**。唯一真正逃不掉"选一个数"的地方 = CoW/日志型 B+tree 节点（RavenFS 树节点）。

## 2. Linux 实测方法学（可复现）

### 2.1 A/B 实验：2×4K 阻塞读 vs 1×8K 阻塞读
- 语义映射：2 次 `pread(4K)` 串行阻塞 = 2 条 NVMe 读命令、2 次 submit+CQ；1 次 `pread(8K)` = 1 条命令
- 测的是"搬同样 8KB 数据的事务总耗时"，A 内部还记录两次 4K 各自耗时（诊断命令开销 vs NAND 时间）
- 关键坑（全部踩过）：
  1. O_DIRECT 绕过 page cache，否则第二次读命中内存，测的是缓存不是盘
  2. ext4 空洞读不走盘 → 必须先真实落盘写一遍窗口
  3. 每轮随机偏移、A/B 测不同位置 → 防设备读缓存/预读命中
  4. A/B 顺序每轮交替 → 抵消温度/频率漂移
  5. **桌面干扰是时间聚类的**：逐尺寸顺序采样会被整组打高 → 用轮转交错采样（所有尺寸按轮次轮流），
     指标用 **min floor**（500×2 次下界，干净信号）而非 p50（被干扰抬升，且随读窗口变大加剧）

### 2.2 T(s) 扫描：延迟 vs 传输大小
- 4K 步进 4K→1MiB（mdts 上限）共 256 点 + 2/4/8/16/32MiB 附加点（Linux 拆多命令行为）
- 实现：`nvme_lat_curve_rr.c`（轮转版）

## 3. 实测结果（两盘基线）

### 3.1 A/B 结果
| 盘 | A: 2×4K p50 | B: 1×8K p50 | 加速比 | 省时 |
|---|---|---|---|---|
| UMIS RPJYJ1T24MLR1HWY (PSLaptop 系统盘) | 97.2µs | 52.2µs | 1.81× | 45% |
| WD Blue SN5000 2TB (nvme1n1, 4Kn) | 111.7µs | 58.4µs | 1.91× | 48% |

诊断：第二次相邻 4K 依然 ~满往返（无控制器读缓存命中）→ 每次 4K 都是实打实一次全往返。
单 4K ≈ 56µs，单 8K ≈ 58µs —— 8K 只贵 2.4µs，收益全来自少付一次固定往返。

### 3.2 T(s) 线性律（WD SN5000，关键结论）
```
T(s) ≈ 60.3µs + 0.198µs/KiB × s     (4K..1MiB 全段, R²=0.992, 基于 min floor)
```
- 固定往返成本 ≈ 60µs（与数据量无关）——唯一大头
- 数据边际每 4K 仅 +0.79µs —— 搬数据本身几乎免费
- >1MiB：Linux 拆 ncmd 条命令并行，边际不变（~0.20µs/KiB 一路平到 32MiB）→ 拆分无额外惩罚
- 曲线图见 `assets/lat_curve_wd_sn5000.png`，全 261 点数据见 `assets/lat_curve_final.csv`

### 3.3 设备特征（对本设计有决定性影响）
| 特征 | 值 | 推论 |
|---|---|---|
| mdts = 8 | 单命令上限 1MiB | 摊销收益 1MiB 封顶；>1MiB 单元不省命令 |
| 4Kn (logical 4096) | — | 对齐要求放宽，4K 粒度天然对齐 |
| **sgls = 0**（PRP only） | — | **PRP 本就每 4K 一条目 → 物理连续零收益 → 缓存单元可用 order-0 散页拼装 → 伙伴碎片项可设计消解** |

## 4. 粒度代价模型 L(g)

```
L(g) = ws·(τc·r/g)            # A 顺序读: 命令摊销(凸, 递减收益)
     + wr·(τc+τ1·r)·cm(g)     # B 随机读: 与 g 几乎无关(容量效率 cm 只在偏斜下咬人)
     + ww·(node_rw + WAF(g)(τcw+τ1·g) + zero)/b(g)   # C CoW 更新: 随 g 线性涨
     + CPU(归零/校验, 可选)
```
- 参数标定来源：τc=τcw=60µs、τ1=0.198µs/KiB ← 本调研实测；WAF 分段 ← NAND 页 16K 典型值（待实测标定）
- 写放大三层拆解：OS 回写层（脏位图 → 4K 回写 → ≈0，设计消解）/ CoW 节点层（真惩罚，随 g 线性）/
  FTL 层（g<16K 部分页写 WAF≈2.5，g≥16K 整页对齐 WAF≈1.15 → **16K 是 CoW 下限台阶**）
- 模型脚本：`assets/cache_gran_model.py`（所有常数带标定来源注释）

### 4.1 场景结果（µs/4K，网格搜索 g∈{4K..1MiB}）
| 场景 | g* | 平坦带(±5%) | 4K 相对代价 |
|---|---|---|---|
| bulk 顺序 80% | 256K | 128–256K | 8.4× |
| mixed 40/30/30 | 128K | 64–256K | 4.6× |
| rand 5/45/50（有写合并 b=8） | 32K | 32–64K | 3.7× |
| sync 每更新落盘（b=1） | **16K** | 16–32K | 1.5×（且 16K 是 NAND 页对齐点） |
| 纯顺序只读 100% | 1MiB（单调递减到命令上限） | — | — |

### 4.2 为什么不推荐 >256K（U 型结构的右支）
1. 摊销收益在 mdts=1MiB 处封顶：64K 时 0.94µs/KiB → 256K 时 0.23 → 1M 时 0.06，之后归零
2. CoW 重写/归零/数据移动随 g 线性涨不封顶（1MiB 一次重写 ≈ 203µs 数据 + ~100µs 归零）
3. 顺序大命令收益可被"命令聚合层"拿走（256K 单元 ×4 条 = 1MiB 命令），单元无需为此变大
4. 灵敏度：关归零、bmax=32 均不改变 g*=256K；唯一让 g* 冲顶的是纯顺序无更新负载

## 5. 现实核查（Linux 侧，本机实测）

### 5.1 全局页缓存计数器读法
| 来源 | 语义 | 坑 |
|---|---|---|
| /proc/meminfo `Cached` | 全局页缓存 kB（≈nr_file_pages×4K − Buffers − SwapCached） | **含 Shmem/tmpfs**；含 Dirty |
| /proc/vmstat `nr_file_pages` 等 | 原始页计数，可拆成分 | 单位是页（×4096） |
| /sys/devices/system/node/nodeN/meminfo | 按 NUMA 节点 | — |
| cgroup v2 `memory.stat` file/file_dirty | 工作负载级页缓存 | 与 meminfo 口径有差，只做同口径前后对比 |
| mincore() | 按文件测驻留率（利用率的操作定义） | 一次 syscall 最多 128 页，需 mmap |

### 5.2 本机文件尺寸分布（验证"<4K 文件一大堆"）
| | /（51.6 万文件/66.9GB） | /home（100.8 万文件/301.8GB） |
|---|---|---|
| <4K 数量占比 | 59.1% | 56.5% |
| <4K 字节占比 | 0.60% | 0.18% |
| >1M 文件（~0.5% 数量）字节占比 | 87.7% | 91.2% |

**<4K 文件确实压倒性多数（两盘 ~87 万个），但只占字节 0.2–0.6%——对页缓存容量的威胁取决于热度而非数量。**

### 5.3 打开文件页缓存驻留（330 个唯一文件，mincore 实测）
- 130 个 <4K 文件中 72 个当前驻留（热小文件 = "一碰就整页留下"，72×4K=288KB）
- 页缓存字节热点 = 1–140MB 的"应用包/数据库"全驻留型：jvm lib/modules 139MB、
  firefox omni.ja ~95MB、vscode .asar 53MB、places.sqlite 43MB、cpptools .browse.VC.db 57MB
- 结论：本机（桌面+开发）热文件 = 中大型顺序对象；小文件"数量热、字节冷"。
  一般规律：字节级热集几乎总在大文件侧；"海量小文件随机读"型负载（解压/小文件服务器）才把热点压到 <8K。

## 6. 设计结论（三层解耦）

```
┌ 层1 扇区脏跟踪/回写:  4K 固定(脏位图, 不变形)     ← 防 OS 层写放大
├ 层2 抓取/预读聚合:    自适应 ≤1MiB(顺序检测)      ← 拿命令摊销收益; 随机按 4K 需求抓
└ 层3 对象/驱逐单元:    32K 起步(见 §7 双桶)        ← 按需 pow2ceil ≥4K, 不按对象预付 32K
```
- 小文件处理：inline 进树节点 / 按 pow2ceil(文件大小) 取块（ZFS 模式），最低 4K——32K 是"上限与聚合粒度"，不是"最小成本"
- 4K 桶/小对象解决的是**容量浪费**，不解决随机读 60µs 命令延迟（那是 block_queue QD 的领域）——验收指标别写错

## 7. 双桶架构构想（2026-09-03 用户 idea + 评估）

**构想**：页缓存分两个内存区间——32K 桶（顺序/大对象）与 4K 桶（小对象）；先全部走 32K 桶，内存浪费压力上来后再研究转换逻辑。

**Raven 评估：方向对，且"区间=桶"形式让转换逻辑便宜一个量级。**

### 7.1 为什么区间制是加分项
- 区间按连续块管理 → 桶间"转换" = **整块迁移（缩边/扩边）+ 冷对象驱逐**，对象级转换只发生在"驱逐后按新策略抓取"
- clean 页转换 = 驱逐即可（下次 miss 重抓），永远不需要原地搬数据；脏页 = 写回再驱逐
- 与 test_set/phy_instance_{1,2}.json 配合：区间边界做成启动参数，两个物理实例扫配比曲线

### 7.2 必须提前埋的三个点
1. **v1 就埋浪费率指标**：每 32K unit 的 live 4K 扇区计数（脏位图扩展成 live 位图，~8bit/unit 开销 0.02%）
   + 滑动窗口 W = Σlive/Σcapacity。否则"压力上来"时只有 free 低一个信号，分不清浪费还是真需求
2. **索引层按 4K 扇区叶子做**（为将来可变粒度留门），转换走"驱逐+重新分类"，禁止原地拆分/合并（搬数据+索引分裂全是坑）
3. **4K 桶对象先按文件分类**（小文件整体 → 4K 桶；顺序文件 → 32K 桶），
   不要先做"大文件的散页进 4K 桶"（一个文件同时活在两桶 → 索引复杂度爆炸）
   分类器 = Linux readahead 每文件状态机的翻版：顺序检测标 32K，小文件/随机标 4K

### 7.3 触发与迟滞（双向都要，防抖）
```
W < 25% 且 free < 低水位 → 新抓取/冷 unit 转 4K 桶（32K 区间缩边）
W > 60% 且 4K 桶有压力  → 顺序流转回 32K（区间扩边）
```
- 起步配比：4K:32K = 1:3（RAM ~28GB 量级），或 100% 32K + 4K 桶 0 容量靠缩边长出来
- 回写粒度恒 4K（脏位图），绝不跟 32K 对象走

### 7.4 落地顺序
1. v1：单 32K 区间 + live 位图/浪费率计数 + 4K 扇区叶子索引（本调研文档配套）
2. v2：区间缩边/扩边 + 文件级分类器 + 驱逐式转换
3. 全程回写 4K 不变
